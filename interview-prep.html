Section 1

Project Overview & Architecture

The big picture — what Volo is, how it's structured, and why each technology was chosen.

What is Volo?

Volo is a local store discovery app for Android. Users open the app, see shops near them on a map or list, browse what's in stock, and visit in person. Store owners can list their shop, add products, and reach nearby customers — all for free with no commission fees. The app is currently in closed testing on Google Play under the package name io.volo.app.

The 3-Tier Architecture

The project is split into three clear layers, each with a single responsibility:

  • Tier 1 — Frontend: A React Native app built with Expo. This is what the user sees and touches on their Android phone. It fetches data from the backend and displays it.
  • Tier 2 — Backend: A FastAPI server written in Python, hosted on Render. This is the brain — it handles business logic, caching, authorization checks, and talks to the database on behalf of the app.
  • Tier 3 — Data Layer: Appwrite Cloud — a hosted database, authentication, and file storage service. The backend reads and writes all data here using a private server API key.
Key design decision: The mobile app never reads or writes store data directly to Appwrite. It always goes through the FastAPI backend. The only thing the app does directly with Appwrite is handle user login (Google Sign-In).

The Git branch is named realestate-to-discount and one environment variable is called APPWRITE_PROPERTIES_COLLECTION_ID — even though it stores shops, not properties. This is because the app started as a real estate listing project and was repurposed. Renaming the env var on the live server carried risk of breaking the deployment, so the name was kept. This is a real-world example of inherited naming debt and pragmatic decision-making.

Section 2

FastAPI Backend Deep Dive

How FastAPI works, how the backend is organized, and what each file does.

What is FastAPI?

FastAPI is a Python web framework for building APIs. Three things make it stand out: it uses Python type hints so you declare what data a function expects and FastAPI enforces it automatically; it uses Pydantic so request bodies are typed Python objects, not raw dictionaries; and it auto-generates interactive API documentation at the /docs URL with zero extra work.

How the Backend is Organized

The backend has four files, each with one job:

  • main.py: The entry point. Creates the FastAPI app, registers the two routers (stores and products), and defines two utility endpoints — a health check and the account deletion page.
  • appwrite_client.py: Sets up the connection to Appwrite using the server API key stored in environment variables. Creates one shared client object that the whole app reuses.
  • cache.py: A simple in-memory cache with a 60-second expiry. Stores data in a Python dictionary so repeated API calls return instantly without hitting Appwrite again.
  • routes/stores.py and routes/products.py: All the actual API endpoint logic, split by resource.

Modular Routing with APIRouter

Instead of putting all endpoints in one giant file, FastAPI lets you split them into separate router files. Each router is like a mini-app. The main file mounts each router with a prefix — so every route inside the stores router automatically gets /stores added to the front of its URL. This keeps the codebase clean and each resource self-contained.

Pydantic Models — Automatic Validation

Every POST and PUT request body is defined as a Pydantic model — a Python class where each field has a declared type. When a request arrives, FastAPI reads the JSON body and tries to build that class from it. If any required field is missing or the wrong type, FastAPI automatically rejects the request with a 422 error and a clear explanation — before your code even runs. Optional fields are declared with a default value of None.

Two model classes exist per resource: one for creating (all required fields mandatory) and one for updating (all data fields optional, so clients can send only what changed).

The Appwrite Client Setup

The Appwrite client is initialized once when the server starts. It reads three values from environment variables — the API endpoint, the project ID, and the server API key. Using environment variables means these secrets never appear in the code or on GitHub. On Render (production), these values are set in the Render dashboard. Locally, they live in a .env file that is gitignored.

The server API key has admin-level access — it can read and write any data in the project. This is why it must never appear in the mobile app. The app uses a limited client session; the backend uses the powerful server key.

How Errors Are Returned

Every route starts with a guard clause — it checks that the required environment variables exist. If they don't, it immediately returns a 500 error with a clear message. For business logic errors like "store not found" or "not authorized," the code raises an HTTPException with the appropriate status code. FastAPI catches this and converts it into a clean JSON error response automatically.

Section 3

REST API Design

What REST is, how your API follows its principles, and a complete map of every endpoint.

Did You Build a RESTful API? Yes.

REST stands for Representational State Transfer. It is a set of rules for designing APIs so that any client can talk to any server in a predictable way. Your API follows all the core rules:

  • URLs are nouns, not verbs. The URL names the thing you're working with — /stores, /products. What you're doing to it (create, read, update, delete) is expressed by the HTTP method, not the URL.
  • HTTP methods as verbs. GET means read. POST means create. PUT means update. DELETE means delete. This is consistent across every endpoint in your API.
  • Status codes communicate results. 200 for success, 403 for forbidden, 404 for not found, 422 for bad input, 500 for server errors.
  • Stateless. Every request contains everything the server needs. The server holds no memory of previous requests. Each call is independent.

Complete Endpoint Map

Path Parameters vs Query Parameters

Path parameters go inside the URL and identify a specific resource. If you're working with a specific store, its ID is in the path: /stores/abc123. Removing it would make the URL meaningless.

Query parameters go after a question mark and configure or filter the request. They change what you get back but don't identify the resource itself. Examples: ?limit=10 controls how many results to return; ?category=Food filters by category.

The Response Envelope

Every response from your API is wrapped in the same shape — an object with a source field and a data field. The source field says whether the data came from Appwrite directly ("db") or from your in-memory cache ("cache"). This is useful for debugging — if you see stale data, the source field tells you immediately why. Mutation responses (create, update, delete) use a simpler shape with an "ok" field.

Important order note: In FastAPI, the route for /stores/my must be declared before /stores/{id} in the code. If the dynamic route came first, FastAPI would match the word "my" as a store ID and fail. Route order matters — specific routes before generic ones.
Section 4

Appwrite & the TablesDB Migration

What Appwrite is, what broke in v1.8, and how you fixed it without touching the frontend.

What is Appwrite?

Appwrite is a Backend-as-a-Service (BaaS). Instead of building a database, an authentication system, and file storage from scratch, Appwrite gives you all three pre-built and hosted in the cloud. You connect to it through an SDK. In Volo, Appwrite handles three things: storing all store and product data, managing user accounts via Google Sign-In, and storing product images.

Two Different Roles in Your Project

Appwrite is used in two different ways depending on who is making the call:

  • Frontend (mobile app): Uses the Appwrite client SDK for Google Sign-In only. The client SDK has limited permissions — a logged-in user can only access their own data.
  • Backend (FastAPI): Uses the Appwrite server SDK with an admin API key. This has full read-write access to all data. It handles all database operations — fetching stores, creating products, deleting records.

What Happened in v1.8 — The Breaking Change

Before Appwrite v1.8, the database API was document-based. You called list_documents and get_document, and responses came back with dollar-sign-prefixed system fields like $id, $createdAt, and $updatedAt.

Appwrite Cloud automatically upgraded to v1.8, which introduced a new row-based API called TablesDB. The method names changed (list_rows, get_row, create_row, delete_row) and the response format changed — system fields lost their dollar sign prefix and became lowercase: id, createdat, updatedat.

The entire frontend was built expecting the old dollar-sign format. When Appwrite upgraded, everything broke overnight — the app couldn't read any store data because the field names had changed.

The Fix — The _normalize() Adapter

Instead of rewriting all the frontend code, a translation function was added to the backend. Every response from Appwrite passes through this function before being sent to the app. It loops through every field in the Appwrite response and renames the system fields back to the dollar-sign format the frontend expects. Regular data fields like "name" and "address" are left completely untouched.

The result: the frontend continues to receive exactly the same shape it always expected. Zero frontend changes were needed. This pattern — putting a translation layer between two systems that speak different formats — is called the Adapter design pattern.

Interview talking point: This is a real example of dealing with a third-party breaking change in production. The adapter pattern was chosen because it isolated the fix to one function in the backend, rather than requiring changes across every screen in the mobile app.

How Appwrite Queries Work

Appwrite has its own query system. Instead of writing SQL, you build query objects — things like "equal this field to this value," "search this field for this text," "order by this field descending," "limit to 10 results." These are passed as a list to the list_rows call and Appwrite handles the actual filtering on its servers.

How Google Sign-In Works

The user taps Sign in with Google. The app opens a browser popup showing Google's login page. The user approves. Google sends confirmation back to Appwrite. Appwrite creates a user session and gives the app a user object with a unique ID. The app stores this ID and sends it as the ownerId in all future API calls. The FastAPI backend never handles login at all — authentication is entirely between the app and Appwrite.

Section 5

Caching Strategy

Why caching was added, how it works, and how it stays accurate when data changes.

Why Cache at All?

Every time the frontend fetches stores, the backend has to make a network call to Appwrite — a cloud service hosted somewhere else. That round trip takes time. If ten users load the app at the same time and all fetch the same store list, that's ten identical Appwrite calls for the same data. Caching means the backend fetches from Appwrite once, stores the result in memory, and returns it instantly for all subsequent requests — until the data changes or 60 seconds pass. This reduces response time, reduces Appwrite API usage, and improves the experience on Render's free tier where resources are limited.

How It Works

The cache is a plain Python dictionary stored in the backend's memory. Each entry stores two things: the actual data, and the timestamp of when it was stored. When a request comes in, the backend first checks the cache. If the data exists and is less than 60 seconds old, it returns it immediately and never contacts Appwrite. If the data doesn't exist or has expired, it calls Appwrite, stores the fresh result in the cache, and returns it.

Cache Keys — How Data is Identified

Every unique combination of request parameters gets its own cache entry. A request for stores with category "Food" is cached separately from a request for all stores. A request for page 2 is cached separately from page 1. The key is a string that encodes all the parameters — for example, "stores:10:0:coffee:Food". This means cached results are always specific to the exact request that created them.

Cache Invalidation — Keeping Data Accurate

The trickiest part of caching is knowing when to throw away old data. When a store is created, updated, or deleted, any cached store lists are now out of date. The fix is prefix-based invalidation — when something changes, all cache entries whose key starts with "stores:" are deleted at once. This clears every paginated and filtered variant in a single operation. For a specific store's cache entry, that exact key is also deleted. This way, the next request always fetches fresh data from Appwrite.

"There are only two hard things in computer science: cache invalidation and naming things." Your caching code demonstrates both — TTL handles automatic expiry, and prefix-based invalidation handles correctness after mutations.

The source Field

Every API response includes a "source" field that says either "cache" or "db". This is a debugging tool — if you're seeing stale or incorrect data, the source field immediately tells you whether it came from Appwrite (fresh) or from the in-memory cache. This kind of built-in observability is a sign of thoughtful API design.

Trade-offs and Limitations

This is an in-process cache — it lives in the memory of the single FastAPI process. This works perfectly on Render's single server instance. The limitation is that if the app were scaled to multiple servers, each server would have its own separate cache and they would go out of sync. The production solution for that scenario would be an external shared cache like Redis — one cache that all server instances read from. For a student project at this scale, the in-process approach is the right pragmatic choice.

Authorization & Security

What security is in place, what's missing, and how to talk about it honestly and confidently.

Authentication vs Authorization — Know the Difference

Authentication is proving who you are. In Volo, this is handled entirely by Appwrite — the user signs in with Google and Appwrite confirms their identity and gives them a user ID.

Authorization is checking what you're allowed to do. In Volo, this is handled by the FastAPI backend — before any update or deletion, the backend checks whether the requesting user actually owns the resource they're trying to change.

The Ownership Check Pattern

Every endpoint that changes data follows the same three steps: first, fetch the record from Appwrite to confirm it exists. Second, compare the ownerId stored in that record against the ownerId sent in the request. Third, if they don't match, return a 403 Forbidden error and stop. Only if they match does the backend proceed with the change. This prevents user A from deleting user B's store — assuming the ownerId sent in the request is genuine.

403 vs 401 — Know the Difference

A 401 Unauthorized means "I don't know who you are — please log in." A 403 Forbidden means "I know who you are, you're just not allowed to do this." Your API correctly uses 403 for ownership failures, because the backend already has an ownerId at that point. The issue is permission, not identity.

The Vulnerability — BOLA

The critical security gap is that the backend trusts the ownerId sent by the client without verifying it is genuine. A simple analogy: imagine a security guard who checks your name matches the register, but never asks to see your ID. Anyone who knows a victim's user ID could send it in a request and pass the ownership check.

This is called BOLA — Broken Object Level Authorization — and it is number one on the OWASP API Security Top 10. In practice, the risk is lower here because Appwrite user IDs are long random strings (hard to guess), and the app is in closed testing. But it is not production-safe.

The proper fix: The app should send its Appwrite session token in the Authorization header of every request. The backend should verify that token with Appwrite's server SDK. The verified user ID from that response — not the client-sent ownerId — should be used for the ownership check. This way, user identity is cryptographically verified server-side, not client-declared.

What Security IS Done Right

  • Secrets in environment variables: The Appwrite API key and all config values are stored as Render environment variables, never in code. If someone reads the GitHub repo, they get nothing sensitive.
  • No SQL injection risk: All database access goes through the Appwrite SDK. There are no raw database queries being built from user input.
  • Type validation: Pydantic rejects malformed input before it reaches business logic. Wrong data types are rejected at the door with a 422 error.
  • HTTPS: Render provides HTTPS automatically. All traffic between the app and the backend is encrypted.
  • Fetch-before-mutate: Every delete and update fetches the record first, so you cannot delete a record that doesn't exist.

What Is Missing

  • No rate limiting — the API has no throttle on how many requests one client can make.
  • No CORS policy configured — any browser-based client could call the API.
  • No input length limits — Pydantic checks types but not maximum string lengths.
  • No JWT verification — ownerId is trusted from the client, not verified via a signed token.

How to Talk About This in an Interview

"The backend has ownership checks — before any mutation I fetch the record and verify the ownerId matches. The current gap is that ownerId is client-declared rather than server-verified via a signed token. The fix is adding Appwrite JWT verification as a FastAPI dependency so user identity comes from a cryptographically verified source, not the request body. I'm aware this is BOLA — OWASP API Top 1 — and it's the next hardening step. For a closed-testing student project with UUID-based IDs, the practical risk is low, but I wouldn't ship this to production without fixing it."

Section 7

React Native Frontend

How the app is structured, how the home screen works, and the key technical patterns used.

React Native + Expo

React Native lets you build mobile apps using JavaScript and TypeScript. Instead of writing Java for Android or Swift for iOS, you write components in React and React Native compiles them to real native UI elements. Expo is a layer on top that handles the painful parts — building, device permissions, location access, and Play Store publishing — without needing Android Studio.

Expo Router — File-Based Routing

Expo Router works like Next.js. The file name determines the screen URL. A file at app/sign-in.tsx becomes the sign-in screen. A file at app/(root)/stores/[id].tsx becomes a dynamic screen where [id] is replaced by an actual store ID. Folders with names in parentheses — like (root) and (tabs) — are organisational groups that don't appear in the URL. The root layout file checks if the user is logged in and redirects to sign-in if not, protecting all inner screens automatically.

Debounced Search

When a user types in the search box, the app does not call the API on every single keystroke. Instead, it waits until the user stops typing for 400 milliseconds before firing the request. This is called debouncing. Typing "coffee" fires one API call instead of six. It works by starting a 400ms countdown every time a key is pressed. If another key is pressed before the countdown finishes, the timer resets. The API is only called when the full 400ms passes without any new input.

Infinite Scroll Pagination

Stores are loaded in batches of 10. When the user scrolls near the bottom of the list, the app automatically loads the next 10 stores and appends them to the existing list. This is more efficient than loading all stores at once — on launch, only 10 rows are fetched instead of potentially hundreds. The app tracks which page it's on and calculates the offset (how many records to skip) for each request. If a batch returns fewer than 10 stores, the app knows it has reached the end and stops trying to load more.

Race Condition Prevention

A race condition happens when two async operations run at the same time and the results arrive in the wrong order. For example: a user types "coffee," then immediately changes to "cafe." Both API calls start. If "coffee" results arrive after "cafe" results, they overwrite the correct data. To prevent this, every new search gets a version number. When results arrive, they check whether they are still the latest request. If a newer request has started since, the old results are silently discarded. Only the most recent request's results are ever shown on screen.

Location-Based Distance Sorting

When the user grants location permission, the app sorts stores by distance — nearest first. Getting the user's location requires asking for permission first, then requesting their current GPS coordinates. The distance between the user and each store is calculated using the Haversine formula, which correctly accounts for the Earth's curvature. You cannot just subtract coordinates because the same degree difference covers different physical distances depending on where on the globe you are. The sorted list is recalculated only when the stores data or location changes, not on every screen render, for performance.

The API Layer — lib/api.ts

All HTTP calls to the FastAPI backend are centralized in a single file called lib/api.ts. No screen makes fetch calls directly. This means if the backend URL ever changes, there is exactly one place to update it. Each function in this file handles building the URL with the right query parameters, making the fetch call, and unwrapping the response envelope — the rest of the app just receives clean data arrays.

Data Validation on the Frontend

Before rendering, every store object is run through a validation function called isValidStore. It checks that the store has an ID, a name, and valid coordinates. Any malformed records from Appwrite are silently filtered out. This defensive approach means a bad record from the database cannot crash the app with a "cannot read property of undefined" error.

The Animated Sidebar

The hamburger menu slides in from the left using React Native's Animated API. The animation runs on the native thread — not in JavaScript — which means it stays smooth at 60 frames per second even if the JavaScript thread is busy doing other work. The sidebar slides in when opened and slides back off-screen when closed, with a semi-transparent dark overlay behind it that dismisses it when tapped.

Section 8

Deployment & Infrastructure

How the backend, app, and website are deployed and run in the real world.

Backend — Render (Free Tier)

The FastAPI backend is deployed on Render, a cloud hosting platform. Render runs the server using uvicorn, an ASGI server for Python. The backend is reachable at https://discount-card-api.onrender.com. On the free tier, the server spins down after a period of inactivity and takes a few seconds to wake up on the next request — this is called a cold start. For a production app, you would upgrade to a paid tier or use a keep-alive ping to prevent this.

All secret values — Appwrite endpoint, project ID, API key, database ID, collection IDs — are stored as environment variables in the Render dashboard. They are never in the code. When the server starts, it reads them using os.getenv().

Mobile App — EAS Build + Google Play

The app is built and published using Expo's cloud build service, called EAS Build. Instead of needing to set up Android Studio locally, you push your code to Expo's servers and they compile it. The output is an AAB file — Android App Bundle — which is the format Google Play requires for submission.

The app is currently in closed testing on Google Play under the package name io.volo.app. Closed testing means only specific testers added by the developer can download and use it. This lets you test on real devices with real Play Store infrastructure before a public launch.

Google Maps Integration

The app uses Google Maps for showing store locations. The Google Maps API key is restricted to the app's package name and SHA certificate fingerprint — meaning even if someone extracts the key from the app, they cannot use it from any other app or website. This is the correct way to secure mobile API keys.

Website — Static HTML on Vercel

The Volo landing page is a static website built with plain HTML, CSS, and JavaScript — no framework. It lives in the website/ folder of the repository and is deployed to Vercel. Vercel serves it as a static site with a global CDN, so it loads quickly anywhere in the world. The website includes the main landing page, a developer page, and a screenshot gallery of the app.

The Delete Account Page

Google Play requires that any app collecting user data must provide a way for users to request account deletion via a publicly accessible URL. A simple HTML page is served directly from the FastAPI backend at /delete-account. It instructs users to email a deletion request. This is the minimum compliance requirement for Play Store listing.

Privacy Policy

A privacy policy is required by Google Play for any app that collects user data (which Volo does — it collects Google account info and location). The privacy policy document lives in the repository and is linked from both the app listing and the website footer.
